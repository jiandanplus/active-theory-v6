# 项目优化方案（最新版）

> 版本：2026-11-04，第 3 版。本版合并并取代以下两份文档：
> - [质量与后台体验修复方案](2026-11-04-quality-and-admin-ux-remediation.md)
> - [数据库评估与性能优化方案](2026-11-04-database-performance.md)

## 1. 目标与约束

**目标：**
1. 修复已经确认的缺陷。
2. 降低公开请求和后台接口的数据库开销。
3. 让静态检查真正覆盖代码。
4. 改善后台的信息展示和操作效率。
5. 降低前端代码的结构复杂度。

**硬约束：**
- **公开网站的前端效果不变。** 原站的 3D 场景、Logo、粒子、布局、交互不变；除了待决策的 D1 之外，每个公开 URL 的状态码、响应头和响应体字节都不变。
- 不改变「草稿 → 预览 → 不可变版本发布」的语义，不自动发布。
- 只做一次表结构变更（迁移 004），必须先备份再升级。
- 每个阶段结束时，`npm run lint`、`format:check`、`typecheck`、`test:launcher`、`npm test` 全部通过，CI 全绿。
- 修改后台界面文字时，同步更新断言这些文字的测试：`tests/admin-modules.test.js`、`tests/content-controls-ui.test.js`。

## 2. 现状依据（2026-11-04 实测）

测量环境：本机 Docker、PostgreSQL 18、Node 24；项目自带的测试夹具和隔离测试库；评审实例用原站内容包安装。

| 类别 | 实测结果 |
|---|---|
| 静态检查 | 现有 lint 只检查 6 组文件，typecheck 只检查 3 个文件。扩大到全仓库后：Prettier 66 个文件不合规；ESLint 报出 `no-unsafe-finally` 2 处、未使用变量 13 处、`==` 1 处、空 catch 2 处、未声明的全局变量 2 处；tsc 报 85 个错误（大多是类型推断噪音） |
| 后台缺陷 | 网站设置的字段顺序错乱，原因是 jsonb 会重排对象的键 |
| 后台体验 | 安装预检报告约 100 行英文内部键名；同一句帮助文字重复十几次；没有运行包时预览和发布按钮仍可点击；场景编辑页的空状态提示有误导性 |
| 公开页面 `/` | 每次请求 17 条 SQL（其中 4 条安装检查重复两遍），6.1 ms；快照每次被哈希 2 次，按真实大小约 1.3 ms CPU |
| `/assets/*` | 每次请求 9–10 条 SQL，同一份快照（真实约 100 KB）读了两次；原站首屏共 93 个素材 |
| `/media/:id` | 300 个真实大小版本时 22 ms，读 2102 个缓冲页，耗时随版本数线性增长 |
| 后台版本列表 | 10 / 50 / 100 个版本分别是 79 / 359 / 709 条查询，37 / 141 / 231 ms |
| 数据规模 | 原站导入后最大的表只有 112 kB；快照原文约 100 KB，压缩后约 34 KB |
| HTTP 缓存 | 页面和素材都是 `Cache-Control: no-store` |

**表结构结论：** 表结构总体合理，包括单例表、乐观锁、不可变版本和制品、摘要约束、最小权限角色，这些都应保持。需要改动的只有一处：「文档型资源引用」没有结构化存储（见 P5）。

## 3. 阶段总览

| 阶段 | 内容 | 是否改表结构 | 风险 | 预计 |
|---|---|---|---|---|
| **S0 安全网** | 黄金对比测试、查询计数测试 | 否 | 无 | 0.5 天 |
| **S1 缺陷修复** | F1–F3 | 否 | 低 | 0.5 天 |
| **S2 工程门禁** | G1–G4（含一次性格式化） | 否 | 低 | 1 天 |
| **S3 读路径性能** | P1–P4、P6、P7 | 否 | 中 | 2–3 天 |
| **S4 后台体验** | U1–U10 | 否 | 中 | 2–3 天 |
| **S5 数据库迁移** | P5（迁移 004） | **是** | 中 | 1 天 |
| **S6 结构重构** | R1–R4 | 否 | 中高 | 3–5 天，每项单独 PR |
| **待决策** | D1–D3 | — | — | 由所有者决定 |

**顺序安排的理由：**
- **S0 放在最前面**：后面的性能优化和重构都需要「输出不变」作为验收依据，所以先把当前输出固定下来。
- **S2 的格式化放在大规模修改之前**：格式化是纯机械改动，先做可以避免和后续改动混在同一份 diff 里，也减少冲突。
- **S3 放在 S6 之前**：P1 先在 `app.js` 里去掉重复的安装检查，R2 拆分中间件时只需要搬移代码，不需要再改逻辑。
- **S4 放在 R1（改用 ES Modules）之前**：先改行为、拿到用户可见的收益，再做模块化。U7 的局部更新按 R1 的接口方式来写，避免重做。
- **S5 单独发布**：这是唯一需要停服升级数据库的一步。

每个条目都按「**问题 / 修复 / 验收**」三部分写。

## S1 · 缺陷修复

### F1. 网站设置的字段顺序错乱
- **问题：** 页面上显示「邮箱显示文字、网站标题、地点三、地点一……」。原因是 [site.js:14](../../../admin-ui/modules/site.js) 用 `Object.entries` 遍历 jsonb 里取出的对象，而 jsonb 会按键长度重排。
- **修复：**
  1. 按 `admin.js` 里 `labels` 定义的顺序渲染；`labels` 中没有的未知键按字母序追加到末尾。
  2. 把「地点一/二/三」改成能看出用途的标签，并加帮助说明。
- **验收：**
  - [ ] 单元测试：传入键顺序被打乱的 `site` 对象，渲染顺序与 `labels` 一致。
  - [ ] 在真实 PostgreSQL 环境中保存、刷新后，顺序不变。
  - [ ] 未知键不会丢失。

### F2. `cas.js` 的 finally 里抛异常，覆盖原始错误
- **问题：** [cas.js:127-136](../../../admin-server/delivery/cas.js) 的清理步骤失败时会直接抛出新错误，前面主流程的错误（例如哈希不匹配、磁盘写满）就丢了。
- **修复：** 记录主流程的错误。主流程失败时，把清理错误挂到原始错误的 `cause` 上，再抛出原始错误；只有主流程成功时，清理错误才直接抛出。安全语义不变：目录身份变化仍然一定导致失败。
- **验收：**
  - [ ] 新增测试：主流程和清理同时失败时，抛出的是原始错误，并且可以通过 `cause` 拿到清理错误。
  - [ ] 现有的 `tests/delivery-*.test.js` 全部通过。

### F3. 静态检查报出的零散问题
- **问题与修复：**
  - [frontend-resources.js:13](../../../admin-server/frontend-resources.js)：`==` 改成显式的 null/undefined 判断。
  - [importers/sqlite.js](../../../admin-server/importers/sqlite.js) 中的两处空 `catch {}`：有意忽略的加注释说明原因，不应忽略的改为记录日志或抛出。
  - 13 处未使用变量（例如 `services/content.js:126 validatedDraft`、`delivery/reader.js:9 cas`）：逐个确认后删除；如果发现是遗漏的逻辑，就补上逻辑并加测试。
  - `engine/program-paths.js` 用到的 `Request`：在 ESLint 中声明为全局变量。
- **验收：**
  - [ ] 按 G1 的配置，这些规则在全仓库零报错。
  - [ ] `npm test` 全部通过。

## S3 · 读路径性能（不改表结构）

**前提依据：** 代码中没有任何更新或删除 versions、delivery_artifacts、runtime_bundles 的语句；交付绑定也只会从「待生成」变成「已固定」一次。所以，「版本号对应的、已经校验过的交付数据」在进程内是确定的，可以缓存。

### P1. 每个请求都把安装检查做两遍
- **问题：** `/` 的 17 条 SQL 中，有 4 条安装检查出现了两次：一次来自 `app.js` 的全局中间件，一次来自 `resolveDelivery`。素材请求和媒体请求也各有 4 条。
- **修复：**
  - 进程内只缓存 `installed` 这一种状态，设 60 秒有效期；安装完成或执行迁移后清空缓存。其他状态（未安装、需升级、不兼容）每次都重新检查。
  - 中间件把查到的状态挂在 `req` 上，`resolveDelivery` 直接复用。
  - `/health/ready` 不走缓存。
- **验收：**
  - [ ] 已安装站点上，缓存有效期内这 4 条查询为 0 次。
  - [ ] 未安装和需升级状态下的 503 页面与 T1 基线一致。
  - [ ] `/health/ready` 每次请求都会查数据库。

### P2. `/assets/*` 把同一份快照读两次
- **问题：** 一次请求里 `SELECT * FROM versions WHERE id=$1` 连续执行两次。按原站规模，首屏要从数据库搬约 93 × 2 × 100 KB ≈ 18 MB 的 JSON。
- **修复：** `resolvePublishedResource` 增加可选参数，可以接收已经取到的 `{id, snapshot}`，不再重复查询。
- **验收：**
  - [ ] 每个 `/assets/*` 请求读取 versions 的次数 ≤ 1（P3 完成后为 0）。
  - [ ] T1 通过。

### P3. 缓存已校验的不可变交付数据
- **问题：** 页面、程序、端点请求每次都会重复读取 binding、artifact、runtime、两份快照和引用列表，并做 2 次快照哈希、1 次 manifest 哈希、1 次引用列表哈希。
- **修复：** 新增 `delivery/cache.js`：
  - 按版本号缓存 `{snapshot, binding, manifest, references}`。
  - 只缓存**完整校验通过且已固定**（artifact_digest 非空）的版本。
  - 用 LRU 限制为 16 个版本，每项 5 分钟后过期，过期后重新完整校验，保留发现数据库被篡改的能力。
  - 每个请求仍然查一次 `published`（主键查找），保证发布立即生效，多实例部署也正确。
  - 预览不缓存。
- **验收：**
  - [ ] 缓存预热后，`/` 和端点请求 ≤ 2 条 SQL，请求路径上 `digestJSON` 调用为 0。
  - [ ] 发布新版本后，下一个请求立刻返回新内容。
  - [ ] 篡改测试：直接修改快照，缓存过期后返回 503（与现有行为一致）。
  - [ ] T1 通过。
  - [ ] `/` 平均耗时比基线 6.1 ms 下降 ≥ 50%。

### P4. 资源状态检查合并为一条查询，公开请求不再查 session
- **问题：**
  - 素材请求要分别查 resources 和 storages 两张表。
  - 只要请求带 Cookie，认证中间件就会查一次 session，公开页面和素材也不例外。
- **修复：**
  - 新增 `getLive(id)`：`resources LEFT JOIN storages` 一次取出资源和它所在存储的状态。回收站、资源状态、存储可用性仍然实时判断，不缓存。
  - session 改为按需加载：只有后台接口、预览，以及需要识别管理员身份的路由才查 session。
- **验收：**
  - [ ] `/assets/*` 每次请求 ≤ 3 条 SQL。
  - [ ] 带 Cookie 访问公开页面时，session 查询为 0。
  - [ ] 资源放入回收站、存储设为不可用后，下一个请求立即返回 404。
  - [ ] 预览的私有性测试全部通过。

### P6. 后台版本列表的 N+1 查询
- **问题：** `listVersions()` 用 `SELECT *` 把所有快照都读出来；[admin-routes.js:50](../../../admin-server/delivery/admin-routes.js) 又在循环里对每个版本做完整校验，每个版本 7 条查询。
- **修复：**
  - 新增 `listVersionHeaders()`，只取 id 和创建时间。
  - 用一条 JOIN 查询批量取出所有版本的绑定和制品信息。
  - 完整性校验复用 P3 的缓存；对没有缓存的版本，只在恢复或查看详情时做完整校验。
- **验收：**
  - [ ] 100 个版本时 ≤ 5 条查询、< 30 ms，查询数不随版本数增长。
  - [ ] 损坏、不支持等状态显示不变。
  - [ ] 响应 JSON 结构不变。

### P7. 保存草稿时逐行插入
- **问题：** `writeLists` 先整表删除，再逐行插入，按原站数据量一次保存约 27 条语句。
- **修复：** 每张表改为一条 `INSERT … SELECT * FROM unnest(...)` 批量插入；仍然在同一个事务里；id 和顺序规则不变。
- **验收：**
  - [ ] 保存 16 个作品时语句数 ≤ 8。
  - [ ] 保存后 `getDraft()` 的结果与优化前逐字节一致。

## S5 · 数据库迁移

### P5. `/media/:id` 全表扫描所有历史快照
- **问题：** `rejectTargetlessDocument` 对所有 versions 和 previews 执行 `jsonb_each` 展开。300 个真实大小的版本时需要 22 ms、读 2102 个缓冲页，并且随版本数线性增长。这一步在每个公开的 `/media/:id` 请求和模型接口上都会执行。
- **修复：**
  - 迁移 `004`：`resource_references` 新增一列 `document boolean NOT NULL DEFAULT false`，从现有快照回填，再建部分索引 `(resource_id) WHERE document AND owner_type IN ('version','preview')`。
  - `collectReferences` 和 `replaceReferences` 写入这一列。
  - 查询改为走这个索引。
  - 在迁移注册表中登记新的结构签名；在 `docs/POSTGRESQL-MIGRATION.md` 中写明升级步骤：备份 → 停服 → 执行 `npm run db:migrate` → 启动。
  - 选择「加一列」而不是新建一张表：判断的粒度和现有引用表一致，原有的写入和清理逻辑可以直接复用。
- **验收：**
  - [ ] 迁移后，新查询与旧查询对所有资源 id 的判断结果一一相同。
  - [ ] `EXPLAIN` 显示新查询走了新索引，300 个版本时 < 1 ms，耗时不随版本数增长。
  - [ ] `schema-upgrade` 测试覆盖从 003 升级到 004。

## 5. 评估后不做的事

| 提议 | 不做的原因 |
|---|---|
| 快照去重（单独建快照表，按摘要引用） | 100 次发布才约 3.4 MB；会破坏版本行自包含、可单独审计的设计，改动面太大 |
| 给多态引用加外键或拆表 | 需要大迁移；改用 R3 的审计兜底 |
| 普遍加索引 | 热点查询都是主键查找（0.01–0.02 ms），表只有几十到几百行，额外索引只会增加写入开销 |
| 引入 Redis 或物化视图 | 单站点、单进程场景下，进程内缓存已经足够 |
| 统一 bigint 时间戳和 timestamptz | 没有性能收益，还有迁移风险 |
| 调整连接池或 PostgreSQL 参数 | S3 完成后查询量会下降一个数量级，现有参数已经足够 |
